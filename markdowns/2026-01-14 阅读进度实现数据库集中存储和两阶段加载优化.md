# 2026-01-14 实现数据库集中存储和两阶段加载优化阅读进度

## 优化目标
解决下载列表初始化时阅读进度加载缓慢的问题，特别是在有大量下载项（100+）的情况下。

## 最终方案：数据库集中存储 + 两阶段加载

### ✅ 核心架构改进

**新增数据库层**：
- 创建 `SPIDER_INFO` 表（SQLite），集中存储所有阅读进度
- 字段：gid, token, pages, startPage, previewPages, previewPerPage, pTokenMapJson, updatedAt, source
- 使用 `MSQLiteBuilder` 创建数据库（`spider_info.db`）

**三层存储架构**：
```
Layer 1: 内存缓存 (LruCache, 200 项)
Layer 2: SQLite 数据库 (持久化)
Layer 3: 文件系统 (.ehviewer 文件)
Layer 4: SMB 网络存储 (3秒超时)
```

**两阶段加载策略**：
```
第一阶段（瞬间 <50ms）：
  ├─► 批量从数据库查询所有进度
  └─► 立即回调 UI，显示已缓存的进度

第二阶段（后台异步）：
  ├─► 4 线程并行检查本地文件/SMB 更新
  ├─► 对比进度是否有变化
  └─► 有更新时自动刷新 UI
```

## 技术细节

### 数据库表结构
```sql
CREATE TABLE SPIDER_INFO (
    GID INTEGER PRIMARY KEY,
    TOKEN TEXT,
    START_PAGE INTEGER NOT NULL DEFAULT 0,
    PAGES INTEGER NOT NULL DEFAULT 0,
    PREVIEW_PAGES INTEGER NOT NULL DEFAULT 0,
    PREVIEW_PER_PAGE INTEGER NOT NULL DEFAULT 0,
    PTOKEN_JSON TEXT,
    UPDATED_AT INTEGER NOT NULL DEFAULT 0,
    SOURCE TEXT
);
```

### 内存缓存策略
- **LruCache**：最多 200 项
- **命中率**：同一个会话内接近 100%
- **内存占用**：约 2-3MB

### SMB 超时控制
- **独立线程池**：2 线程专用于 SMB
- **超时时间**：3 秒
- **降级策略**：超时返回 null，使用数据库缓存

### 后台更新机制
- **智能对比**：只有 `startPage` 或 `pages` 变化时才刷新
- **增量回调**：每个更新独立通知 UI
- **无感知**：用户看不到加载过程

#### 第三步：编译问题修复
**问题1**：Kotlin 类型推断失败
- **现象**：`allowSmb = true` 无法推断类型，`startPage`/`pages` 字段未解析
- **原因**：Kotlin 使用命名参数时类型推断受限
- **解决**：改用位置参数 `true`，添加显式类型 `val newerInfo: SpiderInfo?`

**问题2**：阅读进度更新后显示不刷新

- **解决**：在本地文件写入成功后也立即保存到数据库
