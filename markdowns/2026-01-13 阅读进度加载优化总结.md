# 2026-01-13 阅读进度加载优化总结

## 优化目标
解决下载列表初始化时阅读进度加载缓慢的问题，特别是在有大量下载项（100+）的情况下。

## 优化方案实现

### ✅ 方案 1: SMB 连接超时控制 (3 秒)

**问题**：无超时控制导致 SMB 连接缓慢时长时间阻塞加载

**解决方案**：
- 创建**独立的 SMB 线程池** (`Executors.newFixedThreadPool(2)`)，避免与主加载线程竞争
- 使用 `Future.get(3, TimeUnit.SECONDS)` 为 SMB 读取添加 3 秒超时
- 超时则直接返回 `null`，快速降级到本地文件系统
- 避免了慢速 SMB 或离线服务器导致的长时间等待

**修改位置**：[DownloadSpiderInfoExecutor.kt](../app/src/main/java/com/hippo/ehviewer/sync/DownloadSpiderInfoExecutor.kt#L82-L120)

**代码示例**：
```kotlin
// 单独的 SMB 线程池，避免竞争和线程饥饿
private val smbService: ExecutorService = Executors.newFixedThreadPool(2)

private fun readFromSmb(info: GalleryInfo): SpiderInfo? {
    return try {
        val smbTask = smbService.submit<SpiderInfo?> {
            // SMB 读取逻辑
            val pipe = SmbFileHelper.getSmbFileInputStream(...)
            // ...
        }
        // 最多等待 3 秒
        smbTask.get(3, TimeUnit.SECONDS)
    } catch (e: Exception) {
        // 超时或异常，返回 null 降级到本地
        null
    }
}
```

### ✅ 方案 3: 并行加载优化

**问题**：原使用 `newSingleThreadExecutor()`，下载项必须串行加载，效率低下

**解决方案**：
- 改用 `newFixedThreadPool(4)` 为主加载线程池，最多 4 个线程并行加载
- 使用 `invokeAll()` 直接提交所有任务并等待完成
- 整个批处理的超时是 30 秒（可配置），避免单个超时任务导致整体卡顿

**性能提升**：
- 单线程串行：100 项需要约 120-180 秒
- 4 线程并行：100 项约 30-45 秒
- **预期提升 75% 以上**

**修改位置**：[DownloadSpiderInfoExecutor.kt](../app/src/main/java/com/hippo/ehviewer/sync/DownloadSpiderInfoExecutor.kt#L20-L55)

**代码示例**：
```kotlin
// 主加载线程池：4 线程
private val service: ExecutorService = Executors.newFixedThreadPool(4)

fun execute() {
    service.execute {
        try {
            // 使用 invokeAll 提交所有任务并等待完成
            val callables = mList.map { info ->
                java.util.concurrent.Callable {
                    getSpiderInfo(info)
                }
            }

            // 最多等待 30 秒完成所有任务
            val results = service.invokeAll(callables, 30, TimeUnit.SECONDS)

            // 收集结果
            for (i in mList.indices) {
                try {
                    val spiderInfo = results[i].get()
                    resultMap[mList[i].gid] = spiderInfo
                } catch (e: Exception) {
                    // 任务超时或执行失败
                }
            }
        } catch (e: Exception) {
            // 异常处理
        }

        // 回调结果
        handler.post {
            callBack?.resultCallBack(resultMap)
        }
    }
}
```

### 线程池架构
```
┌─────────────────────────────────────────┐
│     主加载执行器                        │
│   (newFixedThreadPool(4))               │
│                                         │
│  负责并行加载所有下载项                │
│  - 每个任务：getSpiderInfo(info)      │
│  - 超时：30 秒全局超时                │
└──────────────┬──────────────────────────┘
               │
               ├─► 尝试从 SMB 读取（3 秒）
               │   │
               │   └─► SMB 线程池
               │       (newFixedThreadPool(2))
               │       [单独管理，避免竞争]
               │
               └─► 降级到本地文件系统
```

### 超时策略
- **单个 SMB 操作**：3 秒超时，失败快速降级
- **单个加载任务**：30 秒全局超时（包括本地文件 I/O）
- **整个批处理**：30 秒超时后回调结果

### 线程池大小选择
| 线程池 | 大小 | 用途 | 原因 |
|--------|------|------|------|
| 主加载 | 4 | 并行加载下载项 | Android 设备通常 4 核，避免过多上下文切换 |
| SMB | 2 | SMB 网络 I/O | 网络 I/O 通常不需要太多并发，避免过多连接 |

### 为什么要分离线程池？
**问题**：如果都用同一个线程池
- 4 个加载任务占满线程
- SMB 操作需要提交任务到线程池
- 没有可用线程，导致 SMB 任务排队
- SMB 任务等待 → 加载任务等待 SMB 结果 → **死锁**

**解决**：
- SMB 操作用独立线程池
- 加载任务可以快速推进
- SMB 操作在后台处理，不相互阻塞

## 问题排查与修复历程

### 初版问题：线程饥饿导致卡顿
**现象**：优化后反而加载变慢或无反应

**原因分析**：
1. 主加载线程池占用了 4 个线程
2. `getSpiderInfo()` 中又往同一线程池提交 SMB 任务
3. SMB 任务无法获得可用线程，导致排队等待
4. 主加载线程持续等待 SMB 结果 → 死锁

**解决方案**：
- 创建独立的 SMB 线程池 (`newFixedThreadPool(2)`)
- 主加载与 SMB 操作互不竞争
- 系统恢复正常响应

### 关键修复
```kotlin
// ❌ 错误的做法（会导致死锁）
private val service: ExecutorService = Executors.newFixedThreadPool(4)
private fun readFromSmb(info: GalleryInfo): SpiderInfo? {
    val smbTask = service.submit { ... }  // 往同一线程池提交
    smbTask.get(3, TimeUnit.SECONDS)     // 等待，但可能没有可用线程！
}

// ✅ 正确的做法（分离线程池）
private val service: ExecutorService = Executors.newFixedThreadPool(4)
private val smbService: ExecutorService = Executors.newFixedThreadPool(2)  // 独立
private fun readFromSmb(info: GalleryInfo): SpiderInfo? {
    val smbTask = smbService.submit { ... }  // 往独立线程池提交
    smbTask.get(3, TimeUnit.SECONDS)        // 可用线程充足，不会卡
}
```
