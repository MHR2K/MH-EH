## 问题分析

### 之前的性能瓶颈
- **场景**: 2 个 SMB 文件夹 → 扫描需要 9+ 秒，导致 ANR (5 秒超时)
- **根本原因**: 每次查询一个 SMB 目录是否在本地有匹配项时，都要：
  1. 调用 `EhDB.getAllDownloadInfo()` 加载全部 77,977 条下载项
  2. 对每条下载项调用 `getLocalDirectoryName()` → 涉及磁盘 I/O (`SpiderDen.getGalleryDownloadDir()`)
  3. 进行字符串比较
- **复杂度**: O(SMB目录数 × 下载项数) = O(2 × 77,977) = 约 155,954 次操作

### 关键问题代码示例
```kotlin
// ❌ 性能差的实现
private fun findDownloadByLocalDirName(smbDirName: String): DownloadInfo? {
    val allDownloads = EhDB.getAllDownloadInfo()  // 每次都加载全部！
    for (download in allDownloads) {
        val localDir = getLocalDirectoryName(download)  // 涉及磁盘I/O
        if (localDir != null && localDir.equals(smbDirName, ignoreCase = true)) {
            return download
        }
    }
    return null
}
```

### 核心优化：本地目录缓存 + 单次遍历 + 动态进度反馈


## Part 3 概述

本文档说明了 `SMB 映射扫描` 功能的实现要点及最近的复杂度优化，目的是将三种主要扫描方式的时间复杂度统一优化到 O(N + M)：

- N：本地下载项数量
- M：目标 SMB 服务器上的目录总数（多台服务器则为总和）

涉及代码文件：
- `app/src/main/java/com/hippo/ehviewer/smb/SmbMappingScanner.kt`
- `app/src/main/java/com/hippo/ehviewer/ui/fragment/AdvancedFragment.java`

## 三种扫描方式及复杂度对比

1) 从 txt 导入（`smb.txt` 或用户选择的 `.txt`）
	- 描述：解析 txt 文件中每行的 GID（支持 `GID-Title` 或纯 `GID`），用 GID 集合与本地下载匹配后直接保存映射。
	- 复杂度：O(N + K)，其中 K 为 txt 行数（通常 K≈M），等价 O(N + M)。
	- 优点：不访问远端（除首次从 SMB 读取 `smb.txt`），速度最快，网络负担最小。

2) 优先扫描 SMB 服务器（遍历远端目录，在本地查找）
	- 旧实现问题：每遍历一个 SMB 目录就调用 `EhDB.getAllDownloadInfo()` 或对数据库做线性查找，导致最坏 O(M·N)。
	- 优化措施：
		- 预先一次性读取所有本地下载（O(N)），构建 `gid -> DownloadInfo` 的 HashMap（`gidMap`），以及 `localDirCache: lowerName -> DownloadInfo`（O(N)）。
		- 遍历所有 SMB 目录（总计 O(M)），对每个目录：先尝试从 `gidMap` O(1) 查询，再回退到 `localDirCache` O(1) 查询。
	- 优化后复杂度：O(N + M)

3) 优先扫描本地下载（遍历本地项，在 SMB 查找）
	- 旧实现问题：对每个本地下载项，轮询所有服务器并对每台服务器执行 `listDirectory`（或对目录做线性搜索），导致最坏 O(N·M)。
	- 优化措施：
		- 在扫描开始前对每台服务器只调用一次 `listDirectory`（合计 O(M)），构建 `lowercaseDirName -> originalName` 的 HashMap（或 Set）。
		- 随后对 N 个本地下载项，仅做 O(1) 的 membership 查询以判断是否存在对应远端目录。
	- 优化后复杂度：O(N + M)

## 其他工程与行为上的优化点

- 名称规范化：对比时统一使用 `trim()` + `toLowerCase(Locale.US)`。保证不区分大小写且避免空格差异引起匹配失败。
- 可选自适应策略：运行时根据 N 与 M 的相对大小选择最合适策略（例如当 N ≪ M 时选择逐项远端 stat/exists 查询以避免预拉取大量目录）。
- 服务器目录快照缓存（可选）：将每台服务器的目录列表快照到本地（带 TTL 或手动刷新），后续扫描直接读取快照以减少网络调用。
- 并发/限流：多服务器并行列目录时加限流，避免对 SMB 服务器过多并发请求导致失败。

## 已实施的代码改动（摘要）

- 在 `SmbMappingScanner.scanAndCreateMappings` 中一次性构建 `gidMap`（`Map<Long, DownloadInfo>`），替代原先对数据库的重复读取。
- 在 `SmbMappingScanner.scanByLocalDownloads` 中为每台服务器预加载目录列表并构建 `lowerToOriginal` map，然后对本地下载项用 O(1) 查询完成匹配。
- 在 `AdvancedFragment` 中新增/调整导入流程：优先尝试从第一个 SMB 服务器读取 `smb.txt`，失败时回退到系统文件选择器；并把 txt 解析逻辑统一到 `handleCacheFileStream`。

# 2026-01-16 图片解码失败问题 - 修复完成总结

## 📋 问题概述

**现象**：下载完成后进入漫画阅读界面，有小概率会有图片显示解码失败

**严重程度**：中（影响用户体验但不导致崩溃）

**频率**：间歇性（与网络、内存、并发加载等因素相关）

## 🔍 根本原因

### 主要原因 1: Android 9+ 上的解码流程缺陷

`Image.kt` 中的回退机制存在问题：
```
ImageDecoder.decodeDrawable() 失败
    ↓
尝试重置流位置 (source.channel.position(0))
    ↓
调用 BitmapFactory.decodeStream()
```

# 2026-01-13 阅读进度加载优化总结

## 优化目标
解决下载列表初始化时阅读进度加载缓慢的问题，特别是在有大量下载项（100+）的情况下。

## 优化方案实现

### ✅ 方案 1: SMB 连接超时控制 (3 秒)

**问题**：无超时控制导致 SMB 连接缓慢时长时间阻塞加载

**解决方案**：
- 创建**独立的 SMB 线程池** (`Executors.newFixedThreadPool(2)`)，避免与主加载线程竞争
- 使用 `Future.get(3, TimeUnit.SECONDS)` 为 SMB 读取添加 3 秒超时
- 超时则直接返回 `null`，快速降级到本地文件系统
- 避免了慢速 SMB 或离线服务器导致的长时间等待

**修改位置**：[DownloadSpiderInfoExecutor.kt](../app/src/main/java/com/hippo/ehviewer/sync/DownloadSpiderInfoExecutor.kt#L82-L120)

**代码示例**：
```kotlin
// 单独的 SMB 线程池，避免竞争和线程饥饿
private val smbService: ExecutorService = Executors.newFixedThreadPool(2)

private fun readFromSmb(info: GalleryInfo): SpiderInfo? {
    return try {
        val smbTask = smbService.submit<SpiderInfo?> {
            // SMB 读取逻辑
            val pipe = SmbFileHelper.getSmbFileInputStream(...)
            // ...
        }
        // 最多等待 3 秒
        smbTask.get(3, TimeUnit.SECONDS)
    } catch (e: Exception) {
        // 超时或异常，返回 null 降级到本地
        null
    }
}
```

---

### ✅ 方案 3: 并行加载优化

**问题**：原使用 `newSingleThreadExecutor()`，下载项必须串行加载，效率低下

**解决方案**：
- 改用 `newFixedThreadPool(4)` 为主加载线程池，最多 4 个线程并行加载
- 使用 `invokeAll()` 直接提交所有任务并等待完成
- 整个批处理的超时是 30 秒（可配置），避免单个超时任务导致整体卡顿

**性能提升**：
- 单线程串行：100 项需要约 120-180 秒
- 4 线程并行：100 项约 30-45 秒
- **预期提升 75% 以上**

**代码示例**：

```kotlin
private val service: ExecutorService = Executors.newFixedThreadPool(4)

fun execute() {
    service.execute {
        try {
            // 使用 invokeAll 提交所有任务并等待完成
            val callables = mList.map { info ->
                java.util.concurrent.Callable {
                    getSpiderInfo(info)
                }

            // 收集结果
            for (i in mList.indices) {
                try {
                    val spiderInfo = results[i].get()
                    resultMap[mList[i].gid] = spiderInfo
                } catch (e: Exception) {
                    // 任务超时或执行失败
                }
            }
        } catch (e: Exception) {
            // 异常处理
        }

        // 回调结果
        handler.post {
            callBack?.resultCallBack(resultMap)
        }
    }
}
```

```
               │       [单独管理，避免竞争]
               │
```

### 超时策略
- **单个 SMB 操作**：3 秒超时，失败快速降级
- **单个加载任务**：30 秒全局超时（包括本地文件 I/O）

### 线程池大小选择
| 线程池 | 大小 | 用途 | 原因 |
|--------|------|------|------|
| 主加载 | 4 | 并行加载下载项 | Android 设备通常 4 核，避免过多上下文切换 |
| SMB | 2 | SMB 网络 I/O | 网络 I/O 通常不需要太多并发，避免过多连接 |

### 为什么要分离线程池？
**问题**：如果都用同一个线程池
- 4 个加载任务占满线程
- SMB 操作需要提交任务到线程池
- 没有可用线程，导致 SMB 任务排队
- SMB 任务等待 → 加载任务等待 SMB 结果 → **死锁**

**解决**：
- SMB 操作用独立线程池
- 加载任务可以快速推进
- SMB 操作在后台处理，不相互阻塞

## 2026-01-07 SMB自动映射功能实现

### 需求背景
用户通过数据线将漫画复制到 SMB 服务器上，但没有配置 SMB 映射记录。希望应用能**自动检测并读取 SMB 上的同名漫画目录**，无需手动添加映射。

### 实现方案
在 `SpiderDen.openSmbInputStreamPipe()` 方法中添加自动检测逻辑：

#### 工作流程
1. **获取本地目录名**
   - 从 `mDownloadDir` 获取本地下载目录的文件夹名称
   - 例如：`12345-gallery-title`

2. **获取 SMB 服务器配置**
   - 从 `SmbServerStore` 获取已保存的 SMB 服务器列表
   - 使用**第一个服务器**（通常用户只有一个 SMB 服务器）
   - 解析 `relativePath` 得到共享名和基础路径

3. **在 SMB 上查找同名目录**
   - 使用 `Client.listDirectory()` 列出 SMB 上的目录
   - **忽略大小写**匹配本地目录名
   - 例如：`12345-gallery-title` 可匹配 SMB 上的 `12345-GALLERY-TITLE`

4. **直接打开图片**
   - 找到同名目录后，按照优先级尝试打开图片：
     - 优先级 1: `<gid>.cbz` 文件
     - 优先级 2: 该目录下带标准扩展名的图片文件
     - 优先级 3: 列目录查找（处理大小写不一致）

#### 关键优化
- **全自动**：用户感受不到，就像正常打开漫画
- **无需配置**：直接利用已保存的服务器信息
- **兼容性强**：支持大小写差异、CBZ 压缩包、多种扩展名
- **临时映射**：每次动态检测，不保存配置，不污染数据库

### 代码位置
**文件**: `app/src/main/java/com/hippo/ehviewer/spider/SpiderDen.java`

**新增方法**:
- `tryAutoDetectAndOpenSmbInputStreamPipe(int index)`
  - 自动检测 SMB 上的同名漫画目录
  - 解析 SMB 服务器配置
  - 调用 `openSmbFileFromPath()` 打开图片

- `openSmbFileFromPath(Authority, String, String, int)`
  - 从指定 SMB 路径打开图片文件
  - 支持 CBZ 压缩包和普通图片目录
  - 处理大小写和扩展名不一致

**修改方法**:
- `openSmbInputStreamPipe(int index)`
  - 调整优先级：先检查显式映射，再自动检测

### 测试场景

#### 场景 1: 标准目录结构
```
SMB 服务器 /share/Downloads
├── 12345-gallery-title
│   ├── 00000001.jpg
│   ├── 00000002.jpg
│   └── ...
```

**操作**: 打开 gid=12345 的漫画  
**预期**: 自动找到 SMB 上的 `12345-gallery-title` 目录并读取图片  
**日志**: 
```
Auto-detect SMB: found matching dir for gid=12345, 
dirName=12345-gallery-title, smbShare=share, smbPath=Downloads\12345-gallery-title
```

#### 场景 2: CBZ 压缩包
```
SMB 服务器 /share/comics
├── 12345.cbz (包含 00000001.jpg 等)
```

**操作**: 打开 gid=12345 的漫画  
**预期**: 自动找到 `12345-gallery-title` 目录，再发现其中的 `12345.cbz`，从中读取  
**日志**: 
```
Auto-detect SMB: found matching dir for gid=12345, dirName=12345-gallery-title
...
SMB auto-detect gid.cbz success: gid=12345, path=...
```

#### 场景 3: 大小写差异
```
SMB 服务器 /share/comics
├── 12345-GALLERY-TITLE
│   ├── 00000001.JPG
│   └── ...
```

**操作**: 打开 gid=12345 的漫画  
**预期**: 自动匹配（忽略大小写）并正确读取  
**日志**: 
```
Auto-detect SMB: found matching dir for gid=12345, dirName=12345-gallery-title
```

#### 场景 4: 无 SMB 服务器配置
**操作**: 未保存任何 SMB 服务器，尝试打开漫画  
**预期**: 自动检测失败，回退到网络下载  
**日志**: 
```
Auto-detect SMB: no SMB servers configured for gid=12345
```

#### 场景 5: 同名目录不存在
**操作**: SMB 上无同名目录  
**预期**: 自动检测失败，回退到网络下载  
**日志**: 
```
Auto-detect SMB: no matching dir found for gid=12345, 
localDir=12345-gallery-title, smbBase=Downloads
```

### 优先级链
打开漫画图片时的优先级顺序：
1. 本地下载目录（显式存储）
2. 本地缓存目录
3. **SMB（自动检测或显式映射）** ← 新增自动检测逻辑
4. 网络下载（触发 HTTP 请求）

### 调试建议
在 DEBUG 模式下，所有自动检测操作都会输出日志：
```bash

```

关键日志标签：
- `Auto-detect SMB: found matching dir` → 成功发现同名目录
- `Auto-detect SMB: no matching dir found` → 未找到同名目录
- `Auto-detect SMB: no SMB servers configured` → 未配置服务器
- `SMB auto-detect gid.cbz success` → 成功打开 CBZ
- `SMB auto-detect open failed` → 打开单个文件失败

### 后续优化方向
1. **缓存自动检测结果**：第一次成功检测后，临时记忆该映射（会话级），避免重复列目录
2. **支持多个 SMB 服务器**：提示用户选择哪个服务器
3. **手动保存映射**：自动检测成功后，提供"保存映射"选项供用户选择
4. **日志导出**：为调试提供完整的自动检测过程记录

### 兼容性说明
- ✅ 不影响现有的显式 SMB 映射
- ✅ 不影响本地下载和缓存
- ✅ 不影响网络下载
- ✅ 完全向后兼容

## 技术背景

### Jaro-Winkler 算法简介

Jaro-Winkler 相似度算法用于计算两个字符串的相似程度，特别适合短字符串比较：

- **返回值**: 0.0（完全不同）到 1.0（完全相同）
- **优势**: 对前缀匹配给予更高权重，适合搜索场景
- **应用场景**: 模糊搜索、拼写检查、数据去重

**算法原理**:
```
JaroWinklerSimilarity = JaroSimilarity + (prefix_length * scaling_factor * (1 - JaroSimilarity))
```

其中：
- `prefix_length`: 公共前缀长度（最多 4 个字符）
- `scaling_factor`: 权重因子（通常为 0.1）

```java
public static boolean fuzzyContains(String text, String query, double threshold) {
    if (text.contains(query)) {
        return true;
    }
    double maxSimilarity = 0.0;
    for (int i = 0; i <= text.length() - query.length(); i++) {
        String substring = text.substring(i, i + query.length());
        double similarity = calculateJaroWinklerSimilarity(substring, query);
        maxSimilarity = Math.max(maxSimilarity, similarity);
        if (maxSimilarity >= threshold) {
            return true;
        }
    }
    return false;

public static double calculateJaroWinklerSimilarity(String s1, String s2) {
    if (s1.equals(s2)) {
        return 1.0;
    }
    int[] matches = getMatches(s1, s2);
    double m = matches[0];
    if (m == 0) {
        return 0.0;
    }
    double t = matches[1] / 2.0;
    double jaro = (m / s1.length() + m / s2.length() + (m - t) / m) / 3.0;
    int prefix = Math.min(matches[2], 4);
    return jaro + prefix * 0.1 * (1 - jaro);
}

private static int[] getMatches(String s1, String s2) {
    String max, min;
    if (s1.length() > s2.length()) {
        max = s1;
        min = s2;
    } else {
        max = s2;
        min = s1;
    }
    int range = Math.max(max.length() / 2 - 1, 0);
    int[] minIndexes = new int[min.length()];
    Arrays.fill(minIndexes, -1);
    boolean[] maxFlags = new boolean[max.length()];
    int matches = 0;
    for (int mi = 0; mi < min.length(); mi++) {
        char c1 = min.charAt(mi);
        for (int xi = Math.max(mi - range, 0); xi < Math.min(mi + range + 1, max.length()); xi++) {
            if (!maxFlags[xi] && c1 == max.charAt(xi)) {
                minIndexes[mi] = xi;
                maxFlags[xi] = true;
                matches++;
                break;
            }
        }
    }
    char[] ms1 = new char[matches];
    char[] ms2 = new char[matches];
    for (int i = 0, si = 0; i < min.length(); i++) {
        if (minIndexes[i] != -1) {
            ms1[si] = min.charAt(i);
            si++;
        }
    }
    for (int i = 0, si = 0; i < max.length(); i++) {
        if (maxFlags[i]) {
            ms2[si] = max.charAt(i);
            si++;
        }
    }
    int transpositions = 0;
    for (int mi = 0; mi < ms1.length; mi++) {
        if (ms1[mi] != ms2[mi]) {

        }
```

#### 3. `fuzzyContains(text, query, threshold)` - 模糊匹配核心

```kotlin
@JvmStatic
fun fuzzyContains(text: String, query: String, threshold: Double): Boolean
```

**功能**: 判断文本中是否包含与查询字符串相似的子串  
**参数**:
- `text`: 待搜索的文本
- `query`: 查询字符串
- `threshold`: 相似度阈值（0.0-1.0），推荐 0.7

**算法流程**:
1. **快速路径**: 如果精确包含，直接返回 `true`
2. **滑动窗口**: 遍历所有长度等于 `query.length()` 的子串
3. **相似度计算**: 对每个子串计算 Jaro-Winkler 相似度
4. **阈值判断**: 一旦找到相似度 ≥ threshold 的子串，返回 `true`

**示例**:
```kotlin
fuzzyContains("我的英雄学院", "英雄", 0.7)  // true (精确匹配)
fuzzyContains("我的英雄学院", "英隹", 0.7)  // true (相似度 ≈ 0.75)
fuzzyContains("我的英雄学院", "火影", 0.7)  // false (相似度 < 0.7)
```

---

#### 4. `calculateJaroWinklerSimilarity(s1, s2)` - 相似度计算

```kotlin
@JvmStatic
fun calculateJaroWinklerSimilarity(s1: String, s2: String): Double
```

**功能**: 计算两个字符串的 Jaro-Winkler 相似度  
**返回值**: `0.0`（完全不同）到 `1.0`（完全相同）

**算法原理**:
```
JaroWinklerSimilarity = JaroSimilarity + prefix_bonus

其中:
JaroSimilarity = (m/|s1| + m/|s2| + (m-t)/m) / 3
prefix_bonus = p × scaling_factor × (1 - JaroSimilarity)

m = 匹配字符数
t = 换位数
p = 公共前缀长度（最多 4）
scaling_factor = 0.1
```

**特性**:
- 对前缀匹配给予更高权重（适合搜索场景）
- 对字符顺序不敏感（适合处理拼写错误）
- 计算效率高（O(n×m)）

**示例**:
```kotlin
calculateJaroWinklerSimilarity("英雄", "英隹") // ≈ 0.75
calculateJaroWinklerSimilarity("MARTHA", "MARHTA") // ≈ 0.96
calculateJaroWinklerSimilarity("hello", "world") // ≈ 0.47
```

---

#### 5. `getMatches(s1, s2)` - 算法辅助方法

```kotlin
private fun getMatches(s1: String, s2: String): IntArray
```

**功能**: 计算 Jaro-Winkler 算法所需的三个关键指标  
**返回值**: `IntArray(3)` - `[matches, transpositions, prefix]`

**计算逻辑**:

1. **匹配窗口** (match window):
   ```kotlin
   range = max(max.length / 2 - 1, 0)
   ```
   只有在窗口范围内的字符才能被视为匹配

2. **匹配字符** (matches):
   - 两个字符在匹配窗口内
   - 字符相同
   - 每个字符只能匹配一次

3. **换位数** (transpositions):
   - 统计匹配字符中位置不同的数量
   - 用于惩罚字符顺序差异

4. **公共前缀** (prefix):
   - 从字符串开头开始连续相同的字符数
   - 最多计算 4 个字符

**示例**:
```kotlin
getMatches("英雄", "英隹")
// 返回: [2, 0, 1]
// matches=2 (两个字符都匹配)
// transpositions=0 (顺序相同)
// prefix=1 (第一个字符'英'相同)
```

**影响**: 简繁体混搜可能需要更低的阈值

**解决方案**: 
- 配合原有的 `ChineseConvertUtils` 进行简繁转换
- 考虑将阈值调整为可配置项

### 2. 性能开销

**问题**: 模糊搜索比精确搜索慢约 8 倍

**影响**: 大量下载项（> 5000）时可能有明显延迟

**优化方向**:
- 使用协程异步搜索
- 添加搜索结果缓存
- 实现增量搜索

### 3. 阈值固定

**问题**: 阈值硬编码为 0.7，无法根据场景调整

**建议**: 将阈值作为设置项暴露给用户

# 2025-11-13 删除与下载项增强说明

本文记录本次在“下载”和“列表长按菜单”两处交互上的增强：
- 删除时可“仅删除图片文件，不移除下载项”
- 列表新增“仅添加下载项”（不立即开始下载）

## 背景
- 需要在删除下载内容时，支持只清理磁盘图片、保留下载条目，便于之后重新下载。
- 需要在列表中支持只添加下载条目到下载列表，但暂不启动下载任务。

## 功能一：批量删除新增“仅删除图片文件（不移除下载项）”

- 入口：下载列表 -> 选择模式（多选）-> 删除按钮
- 对话框：采用“双复选框”的样式，包含：
  - 删除图片文件（沿用原有选项）
  - 仅删除图片文件（不移除下载项）
- 交互规则：
  - 不勾选任何：仅从下载列表移除条目，不删除图片（与原行为一致）。
  - 仅勾选“删除图片文件”：移除下载项并同时删除图片（与原行为一致）。
  - 勾选“仅删除图片文件（不移除下载项）”：
    - 仅删除图片文件，保留下载项。
    - 将下载项状态重置为可重新下载：`state=NONE`，清零 `finished/downloaded/speed/remaining`，必要时将 `total<0` 归零。
    - 清理下载目录映射：`EhDB.removeDownloadDirname(gid)`。
    - 异步删除目录：`deleteFileAsync(UniFile...)`。
  - 为避免语义冲突：勾选“仅删除图片文件（不移除下载项）”时，会禁用“删除图片文件”的复选框。

- 代码主要变更：
  - `app/src/main/java/com/hippo/ehviewer/ui/scene/download/DownloadsScene.java`
    - 批量删除对话框逻辑：由单选项改为双复选框，新增“仅删图”路径并重置 DownloadInfo。
  - 字符串新增：
    - `download_remove_option_images_only`（中英文）
    - 保留了早先的 `download_remove_option_keep_item` / `download_remove_option_remove_all`（当前未使用，后续如需可切回单选模式）。

- 使用步骤：
  1) 在下载列表长按进入多选，勾选若干下载项。
  2) 点击删除，按需要勾选“删除图片文件”或“仅删除图片文件（不移除下载项）”。
  3) 确认后执行相应操作，列表会刷新显示。

- 注意事项：
  - “仅删除图片文件”会保留条目，但清空本地文件与目录映射；该条目可直接“开始下载”重新拉取图片。

## 功能二：列表长按菜单新增“仅添加下载项”

- 入口：画廊列表（如首页/搜索结果） -> 长按某一项 -> 弹出菜单。
- 新增菜单项：`仅添加下载项`（图标：`v_plus_dark_x24`）。

    - 否则弹出标签选择对话框，可勾选“记住下载标签”，选择后执行添加（同样不启动下载）。

# 2025-11-13 导入压缩包多选与CBZ支持改造

## 背景
- 原有“导入漫画(压缩包)”仅支持单个 `.zip`，且导入后处理流程不统一。
- 本次改造目标：
  - 支持多选导入，且兼容 `.cbz`；
  - 导入时可选择“导入为 CBZ”或“导入为图片”；
  - 增强导入过程可视化（进度 N/M、失败项详情）；
  - 修复封面缺失与状态卡在“等待中”的问题。

## 功能与行为变更
- 多选与类型支持：
  - 选择器支持多选（`Intent.EXTRA_ALLOW_MULTIPLE=true`）。
  - 识别 `.zip` 与 `.cbz`（放宽 MIME，导入端以扩展名校验 `ArchiveSupportUtils`）。

- 导入模式（单选）：
  - 导入为 CBZ：
    - 重打包为标准命名与序号（`%08d.ext`），生成缩略图 `.thumb`，写入 `SpiderInfo`；
    - 直接标记任务为“已完成”（`STATE_FINISH`），下载页可立即阅读。
  - 导入为图片：
    - 按排序解包为图片至下载目录，生成缩略图 `.thumb`，写入 `SpiderInfo`；
    - 亦标记为“已完成”（统一化体验，避免卡在“等待中”）。

- 进度与失败可视化：
  - 导入期间展示“正在导入：N/M”。
  - 若存在失败：在页面下方输出失败清单（文件名 + 原因），并保留在当前页；仅全部成功时自动跳转至下载页。

- 封面与状态修复：
  - 缩略图生成后明确设置 `downloadInfo.thumb = ".thumb"`，确保封面展示正确。
  - 导入完成统一设置：`total=pages`、`finished=pages`、`downloaded=pages`、`state=STATE_FINISH`。
  - 通过 `DownloadManager.addDownload(GalleryInfo, null, STATE_FINISH)` 加入下载列表，并 `EhDB.putDownloadInfo(downloadInfo)` 更新计数，避免状态停留“等待中”。

1) 选择文件

  - 图片模式：直接按序写出图片文件；

- 写入 `SpiderInfo`（`pages`、`pTokenMap` 等）；
- 置状态为 `FINISH` 并入库；
- 汇总导入结果，展示进度与失败详情。

# 2025-10-29 SMB 功能实现与后续修正汇总

### 时间线概述
1. 初始实现：引入 `SmbHelper` 与 `SmbExporter`，完成基础连接、认证、共享列出与文件上传。
2. 编译修正阶段：处理异常层级（移除多余的 `SMBApiException` 捕获）、lambda 变量“需为 final”问题、进度回调逻辑整理。
3. 功能扩展：新增下载项存储位置指示与筛选（见上方章节）。

### 核心类与职责
- `SmbHelper`：
	- 创建 SMB 客户端 (`createClient`) 与连接 (`connectToServer`)。
	- 目录与文件操作：列出共享 (`listShares`)、列出目录文件 (`listFiles`)、上传文件 (`uploadFile`)、确保目录存在 (`ensureDirectoryExists`)。
	- 连接缓存：避免重复 TCP 连接创建，集中关闭与释放。
	- 统一异常包装：将 SMB 运行期异常转换为更易读的 `IOException` 信息。
- `SmbExporter`：
	- 聚焦单个画廊（下载条目）批量文件上传到远程共享路径。
	- 处理目录结构创建、文件名合法化、进度计算与回调。
	- 使用 `AsyncTask` 封装异步导出流程（后续可演进为协程 / WorkManager）。

### 关键技术点
- 认证：`AuthenticationContext(username, password.toCharArray(), domain)`；端口默认 445。
- 访问权限：`EnumSet.of(AccessMask.GENERIC_WRITE)` + 共享访问 `SMB2ShareAccess.FILE_SHARE_WRITE`。
- 创建/覆盖策略：`SMB2CreateDisposition.FILE_OVERWRITE_IF` 保证重复上传时不失败。
- 文件属性：使用 `EnumSet<FileAttributes>` 设置 `FILE_ATTRIBUTE_NORMAL`，保持与 Windows 兼容性。
- 资源释放：`try-with-resources` + 显式 `remoteFile.close()`，防止句柄泄漏。

### 已修正问题
| 问题 | 原因 | 解决方案 | 影响 |
|------|------|----------|------|
| 多余异常捕获 | `SMBApiException` 是 `SMBRuntimeException` 子类 | 合并为单一父类捕获 | 减少重复代码，避免编译器警告/错误 |
| Lambda 非 final 变量 | 上传进度回调中使用循环变量 `count` | 引入 `final int currentCount = count` | 通过编译、语义不变 |
| 进度回调与最终进度同步 | 仅在循环尾更新，用户感知不平滑 | 回调内与循环后双位置发布进度 | 更及时的 UI 反馈 |
| 目录创建失败重试 | 父目录不存在时 mkdir 抛异常 | 递归 `ensureDirectoryExists` + 再次存在性检查 | 避免偶发竞态 |

### 进度计算策略
- 单文件上传内部使用流式写入 + 外层基于已完成文件数比例：`count * 100 / files.length`。
- 可后续扩展为基于“总字节”精准进度（需汇总大小并在 `uploadFile` 回调中传递已写入累计值）。

### 测试建议摘要
1. 基础连接：验证能成功列出共享（常用 `C$`, `Users`, `Public` 等）。
2. 单文件上传：尝试小文件（<100KB）验证创建权限与命名合法化。
3. 大文件传输：观察是否存在超时（默认 10s socket + op timeout，可调）。
4. 断网恢复：上传过程断开 Wi-Fi，确认失败路径与错误信息清晰。
5. 权限不足：对只读共享路径上传，验证异常转换与日志输出。
6. 目录多层创建：上传到尚不存在的多层路径，确认递归 mkdir 正常。

### 当前适用与局限
- 适用：中小批量文件（章节图片）迁移；用户手动触发的导出动作。
- 局限：
	- 未做断点续传（失败需整体重试）。
	- 未做并发多文件同时上传（串行可能影响总耗时）。
	- 未做超时/重试策略的细粒度控制（统一 SmbConfig 超时）。
	- 使用 `AsyncTask` 在较新 Android 版本上可替换为更现代的异步机制。

### 后续可演进方向
1. 引入“总字节进度”与剩余时间估算。

# 2025-09-30 下载标签导入优化

## 问题背景

在数据导入（备份还原）过程中，下载标签（DownloadLabel）的处理存在以下问题：

1. 导入后标签的排序顺序丢失，特别是手动排序（通过拖拽）后的顺序无法保留
2. 对于不再存在的标签，其下载项需要妥善处理，避免丢失
3. 同名标签的处理需要确保一致性，避免重复

## 实现方案

### 标签导入顺序优化

1. 修改了标签导入机制，确保导入时保留原始时间戳（time 属性）
2. 添加了 `addDownloadLabelWithTime` 方法，专门用于导入时保留标签的原始排序信息

```java
public static synchronized DownloadLabel addDownloadLabelWithTime(DownloadLabel raw) {
    // Reset id
    raw.setId(null);
    DownloadLabelDao dao = sDaoSession.getDownloadLabelDao();
    
    // 确保保留原始时间戳
    if (raw.getTime() <= 0) {
        raw.setTime(System.currentTimeMillis());
    }
    
    raw.setId(dao.insert(raw));
    return raw;
}
```

### 不存在标签的处理

对于导入数据中包含的、但在当前系统中不存在的标签：
- 不再自动创建这些标签（可能是用户已经删除的）
- 将这些标签下的下载项移动到默认列表，确保内容不会丢失

### 同名标签的处理

当导入的标签与已有标签同名时：
1. 检查是否已存在同名标签
2. 如果存在，使用已有的标签，不创建新标签
3. 将导入的下载项关联到已有标签上

```java
public static synchronized DownloadLabel addDownloadLabel(DownloadLabel raw) {
    // Reset id
    raw.setId(null);
    DownloadLabelDao dao = sDaoSession.getDownloadLabelDao();
    
    // 检查标签是否已存在
    QueryBuilder<DownloadLabel> queryBuilder = dao.queryBuilder()
            .where(DownloadLabelDao.Properties.Label.eq(raw.getLabel()));
    List<DownloadLabel> result = queryBuilder.list();
    if (!result.isEmpty()) {
        return result.get(0);
    }
    
    // 保留原始时间戳
    if (raw.getTime() <= 0) {
        raw.setTime(System.currentTimeMillis());
    }
    
    raw.setId(dao.insert(raw));
    return raw;
}
```

## 优化效果

1. **保留排序顺序**：导入后标签的排序顺序与导出前一致，特别是手动排序的顺序也能保留
2. **避免冗余**：已删除的标签不会被重新创建，保持系统整洁
3. **数据完整性**：所有下载项都能正确关联到标签，不会因标签缺失而丢失
4. **一致性**：同名标签会被正确处理，避免出现重复标签

## 技术细节

标签排序使用 `time` 属性（时间戳）来维护顺序，这一机制在整个应用中是一致的：

- `moveDownloadLabel` 方法通过调整 `time` 值来实现标签拖拽排序
- 在导入时保留原始时间戳可确保导入后的排序与导出前一致
- 对于同名标签，优先使用系统中已有的标签，保留其原有排序位置

# 2025-09-25 自动备份功能说明

## 功能概述

本功能实现了EhViewer应用的自动数据备份功能，每天在应用第一次启动时自动在后台执行数据库备份。

## 功能特性

1. **自动触发**: 每天第一次启动应用时自动检查并执行备份
2. **后台运行**: 备份过程在后台线程执行，不影响用户操作
3. **智能清理**: 自动清理旧备份文件，保留指定天数的备份
4. **容错处理**: 完善的错误处理和日志记录
5. **配置灵活**: 可通过设置调整备份参数

## 配置选项

在 `Settings` 类中添加了以下配置项：

- `KEY_AUTO_BACKUP_ENABLED`: 自动备份开关（默认开启）
- `KEY_LAST_BACKUP_TIME`: 记录上次备份时间
- `KEY_BACKUP_RETENTION_DAYS`: 备份保留天数（默认7天）

## 备份文件存储

备份文件存储在：`EhViewer/backup/` 目录下

文件命名格式：`backup_YYYYMMDD_HHmmss.db`

例如：`backup_20250101_120000.db`

## 实现原理

### 1. 触发时机
在 `EhApplication.onCreate()` 方法中添加备份检查逻辑，每次应用启动时：
- 检查自动备份是否启用
- 检查距离上次备份是否超过24小时
- 满足条件时执行备份

### 2. 备份过程
- 使用现有的 `EhDB.exportDB()` 方法导出数据库
- 在后台线程执行避免阻塞UI
- 生成带时间戳的备份文件名

### 3. 清理机制
- 按文件修改时间排序，保留最新的备份
- 删除超过保留天数的旧备份文件
- 完善的错误处理和日志记录

## 容错处理

1. **备份过程中应用关闭**: 备份在独立线程执行，中断不会影响主应用
2. **存储空间不足**: 有异常捕获和日志记录
3. **文件操作失败**: 有重试机制和错误日志

## 测试验证

创建了测试工具 `test_backup.java` 用于验证：
- 备份文件命名规范
- 文件排序逻辑
- 清理策略正确性

## 使用建议

1. 默认配置即可满足大多数用户需求
2. 如需调整备份频率，可修改时间间隔检查逻辑
3. 可根据存储空间调整备份保留天数
